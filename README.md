# dart_sqlite

A dependency-free, pure-Dart SQLite-compatible engine for synchronous Dart VM applications. It reads and writes SQLite 3 database files without native SQLite or FFI.

> Status: experimental and application-focused. “SQLite-compatible” describes the database file format and the subset listed below; it does not mean full SQLite SQL semantics or a drop-in replacement for every `package:sqlite3` API.

## What it provides

- In-memory databases and persistent database files.
- Positional SQL parameters, transactions, and synchronous `execute` / `select` APIs.
- SQLite table/index B-trees, overflow pages, rollback-journal recovery, and WAL read/write support.
- A small `sqlite3.open` facade for call sites using `execute`, `select`, `updatedRows`, and `dispose`.
- No runtime package dependencies.

## Install

This package is not published on pub.dev. Use a path dependency:

```yaml
dependencies:
  dart_sqlite:
    path: ../dart_sqlite
```

Adjust the path relative to the consuming project's `pubspec.yaml`.

## Quick start

```dart
import 'package:dart_sqlite/dart_sqlite.dart';

void main() {
  final db = PureDatabase.memory();
  try {
    db.execute('''
      CREATE TABLE users (
        id INTEGER PRIMARY KEY,
        name TEXT NOT NULL
      )
    ''');
    db.execute('INSERT INTO users (name) VALUES (?)', ['Ada']);

    final rows = db.select(
      'SELECT id, name FROM users WHERE id = ?',
      [1],
    );
    print(rows.single['name']); // Ada
  } finally {
    db.close();
  }
}
```

Use `PureDatabase.open(path)` for a persistent file. `PureDatabase.transaction` commits on success and rolls back when the callback throws. Nested transactions are not supported for persistent databases.

## Supported SQL

`execute()` accepts one statement or a semicolon-separated script. Bind values
with a positional list or a map for named placeholders. A trailing semicolon is
optional.

| Area | Supported subset |
| --- | --- |
| DDL | `CREATE [TEMP/TEMPORARY] TABLE [IF NOT EXISTS]` and `CREATE [TEMP/TEMPORARY] TABLE [IF NOT EXISTS] ... AS SELECT` (including a leading `WITH`); `CREATE [TEMP/TEMPORARY] VIRTUAL TABLE [IF NOT EXISTS] ... USING registered_module(args)`; `CREATE [TEMP/TEMPORARY] VIEW [IF NOT EXISTS]` with optional output-column names and a `SELECT` or `WITH` query; `CREATE [TEMP/TEMPORARY] [UNIQUE] INDEX [IF NOT EXISTS]` on columns or deterministic expressions, including partial indexes (temporary indexes require a temporary table); `CREATE [TEMP/TEMPORARY] TRIGGER [IF NOT EXISTS]` for `BEFORE` / `AFTER` table events and `INSTEAD OF` view events; `DROP TABLE` / `DROP VIEW` / `DROP INDEX` / `DROP TRIGGER [IF EXISTS]`; `ALTER TABLE ... ADD [COLUMN]` with declared types, `NOT NULL`, literal `DEFAULT`, `CHECK`, `REFERENCES`, and `COLLATE` (but not `PRIMARY KEY` or `UNIQUE`); `ALTER TABLE ... RENAME TO`; and basic `ALTER TABLE ... RENAME COLUMN` / `DROP COLUMN`; `INTEGER PRIMARY KEY AUTOINCREMENT` |
| DML | Multi-row `INSERT [OR ABORT\|FAIL\|IGNORE\|REPLACE\|ROLLBACK] INTO ... VALUES (...)`, `DEFAULT VALUES`, and `INSERT ... SELECT`; `REPLACE INTO` is the `INSERT OR REPLACE` alias; `WITH` / `WITH RECURSIVE` prefixes for `INSERT`, `UPDATE`, and `DELETE`, plus `INSERT INTO ... WITH ... SELECT`; ordered `ON CONFLICT` clauses with column or expression conflict targets; `UPDATE [OR ABORT\|FAIL\|IGNORE\|REPLACE\|ROLLBACK] ... SET ... [WHERE ...]`; `DELETE FROM ... [WHERE ...]`; each supports `RETURNING` expressions |
| Query | `SELECT` with or without `FROM`, top-level multi-row `VALUES`, derived tables in `FROM` and joins, comma-separated `FROM` sources (implicit cross joins), JSON table-valued `json_each` / `json_tree` / `jsonb_each` / `jsonb_tree` sources, `WITH` CTEs (accepts `MATERIALIZED` / `NOT MATERIALIZED` hints; recursive form supports one or more anchor terms followed by recursive arms using one consistent `UNION` or `UNION ALL` operator, as required by SQLite), inline and named window `OVER` clauses with `PARTITION BY` / `ORDER BY`, window chaining, `ROWS` / `GROUPS` / `RANGE` frames, and frame `EXCLUDE` modes, `WINDOW name AS (...)` definitions, `UNION` / `UNION ALL` / `INTERSECT` / `EXCEPT`, `DISTINCT`, `AS` aliases, `WHERE`, inner/left/right/full/cross/natural joins with `ON` or `USING`, `GROUP BY`, `HAVING`, expression/ordinal `ORDER BY [ASC|DESC] [NULLS FIRST|LAST]`, `LIMIT`, and `OFFSET`; `*`, qualified columns, and rowid aliases (`rowid`, `_rowid_`, `oid`) are supported in queries and DML when not shadowed by declared columns. `LIKE`, `GLOB`, `REGEXP`, and `MATCH` / `NOT MATCH` operators are supported; `MATCH` requires a registered `match(pattern, value)` function. |
| Schema constraints | Column `PRIMARY KEY`, `UNIQUE`, `NOT NULL`, literal `DEFAULT`, `CHECK`, and `REFERENCES`; table-level primary key, unique, foreign key, and `CHECK` constraints; foreign-key `ON DELETE` / `ON UPDATE` actions `NO ACTION`, `RESTRICT`, `CASCADE`, `SET NULL`, and `SET DEFAULT` |
| Collations | `BINARY` and ASCII `NOCASE` on columns, index terms, and UPSERT targets; `ORDER BY ... COLLATE NOCASE` |
| Transactions | `BEGIN [DEFERRED\|IMMEDIATE\|EXCLUSIVE]`, `COMMIT` / `END`, `ROLLBACK`, and nested `SAVEPOINT` / `ROLLBACK TO [SAVEPOINT]` / `RELEASE [SAVEPOINT]` |
| Maintenance | `ANALYZE [schema]`, with optional `[schema.]table` or `[schema.]index` target; `REINDEX` with optional `[schema.]index`, `[schema.]table`, or collation target; `VACUUM [schema] [INTO filename]` |
| Database attachment | `ATTACH DATABASE expression AS schema` and `DETACH [DATABASE] schema`; accepts filesystem paths, `':memory:'`, empty temporary databases, and `file:` URIs with `mode=ro`, `rw`, `rwc`, or `memory`; attached schemas support qualified/unqualified reads, DDL, `INSERT` / `UPDATE` / `DELETE` (including `RETURNING`), maintenance statements, and supported schema-qualified PRAGMAs |
| Parameters | Positional `?` and numbered `?NNN`; named `:name`, `@name`, and `$name` placeholders; use a list in slot order or a map with names and/or 1-based slot keys (`1`, `?1`). Values can be `null`, numbers, strings, booleans, or `List<int>` blobs |

Expressions support literals (including `X'hex'` blob literals), column references, row-value comparisons and `IN` lists/subqueries, parentheses, searched `CASE`, unary and arithmetic operators, comparisons, `IS [NOT] [DISTINCT FROM]`, `BETWEEN`, `LIKE` / `GLOB` / `REGEXP`, `MATCH` / `NOT MATCH` (when a `match(pattern, value)` function is registered), scalar `IN` lists and subqueries, `EXISTS`, bitwise operators, concatenation, JSON extraction operators `->` / `->>`, and `CAST`. Multi-column assignments are supported in `UPDATE` and UPSERT `DO UPDATE`. Scalar and correlated scalar subqueries are supported in expressions. Single-quoted strings, `--` line comments, and block comments are supported. Unquoted identifiers accept Unicode letters and digits; double-quoted, backtick, and bracket identifiers are also accepted.

### Functions

- Math: `ACOS`, `ACOSH`, `ASIN`, `ASINH`, `ATAN`, `ATAN2`, `ATANH`, `CEIL` / `CEILING`, `COS`, `COSH`, `DEGREES`, `EXP`, `FLOOR`, `LN`, `LOG`, `LOG10`, `LOG2`, `MOD`, `PI`, `POW` / `POWER`, `RADIANS`, `SIGN`, `SIN`, `SINH`, `SQRT`, `TAN`, `TANH`, and `TRUNC`. Out-of-domain or non-finite results return `NULL`.
- Aggregates: `AVG`, `COUNT`, `GROUP_CONCAT` / `STRING_AGG`, `JSON_GROUP_ARRAY`, `JSON_GROUP_OBJECT`, `JSONB_GROUP_ARRAY`, `JSONB_GROUP_OBJECT`, `MAX`, `MEDIAN`, `MIN`, `PERCENTILE`, `PERCENTILE_CONT`, `PERCENTILE_DISC`, `SUM`, and `TOTAL`; single-argument aggregates support `DISTINCT`, and `COUNT(*)` is supported.
- Window functions: `ROW_NUMBER`, `RANK`, `DENSE_RANK`, `PERCENT_RANK`, `CUME_DIST`, `NTILE`, `LAG`, `LEAD`, `FIRST_VALUE`, `LAST_VALUE`, `NTH_VALUE`, and the listed aggregates over default or `ROWS` frames. Window `ORDER BY` supports `NULLS FIRST` / `NULLS LAST`; aggregate calls support `FILTER (WHERE ...)` in grouped queries and aggregate windows.
- Runtime identity: `SQLITE_VERSION()` and `SQLITE_SOURCE_ID()` report the SQLite 3.51.0 compatibility reference; this does not imply full SQLite 3.51.0 behavior.
- JSON subtype: `SUBTYPE(X)` reports SQLite's JSON text subtype `74` for supported direct JSON-producing expressions, and `0` for JSONB blobs and ordinary SQL values.
- Scalar, aggregate, and window-only user-defined functions can be registered per database with `registerFunction`, `registerAggregateFunction`, and `registerWindowFunction`; exact-arity and variadic overloads are supported. Aggregate callbacks receive the argument list for each input row and can also be used as window aggregates with `OVER`.
- Date functions accept ISO-8601, Julian-day, `unixepoch`, and `auto` inputs plus `now`; modifiers include second-through-year shifts, `start of day|month|year`, `weekday`, `floor` / `ceiling`, `utc` / `localtime`, and `subsec` / `subsecond`. `localtime` uses the Dart process's local timezone, and precision is limited to milliseconds. `strftime()` supports SQLite's documented substitutions `%d`, `%e`, `%f`, `%F`, `%G`, `%g`, `%H`, `%I`, `%j`, `%J`, `%k`, `%l`, `%m`, `%M`, `%p`, `%P`, `%R`, `%s`, `%S`, `%T`, `%U`, `%u`, `%V`, `%w`, `%W`, `%Y`, and `%%`; unknown substitutions return `NULL`. `timediff(A, B)` accepts two ISO-8601 or Julian-day values (without modifiers) and returns SQLite's calendar-aware `(+|-)YYYY-MM-DD HH:MM:SS.SSS` shift; date/time behavior is still not a full compatibility layer.
- `RANDOMBLOB` / `ZEROBLOB` are limited to 16 MiB per result.
- `base64()` and `base85()` are bundled compatibility extensions: they encode BLOBs to newline-terminated text and decode text to BLOBs. They are not SQLite core functions; other loadable extensions are not supported ([SQLite base64](https://sqlite.org/base64.html), [SQLite base85](https://sqlite.org/base85.html)).

### Supported PRAGMAs

Read/write settings: `analysis_limit`, `application_id`, `automatic_index`, `schema_version`, `user_version`, `foreign_keys`, `defer_foreign_keys`, `recursive_triggers`, `ignore_check_constraints`, `query_only`, `read_uncommitted`, `case_sensitive_like`, `count_changes`, `full_column_names`, `short_column_names`, `legacy_alter_table`, `reverse_unordered_selects`, `busy_timeout`, `cache_size`, `default_cache_size`, `page_size`, `max_page_count` (persistent `main` and reported TEMP state), `mmap_size`, `secure_delete`, `synchronous`, `temp_store`, `wal_autocheckpoint`, `journal_size_limit`, `threads`, and `journal_mode` (`DELETE`, `TRUNCATE`, `PERSIST`, `MEMORY`, `OFF`, or `WAL` for persistent `main`; in-memory databases report `memory` by default and accept `OFF`; TEMP defaults to `delete`). `shrink_memory` is also accepted as a command. Read-only inspection includes `integrity_check`, `quick_check`, `table_info`, `table_xinfo`, `index_list`, `index_info`, `index_xinfo`, `foreign_key_list`, `foreign_key_check`, `database_list`, `table_list`, `collation_list`, `function_list`, `module_list`, `pragma_list`, `compile_options`, `encoding`, `page_count`, `freelist_count`, `auto_vacuum`, and `wal_checkpoint(NOOP)`. Read-only inspection pragmas other than `wal_checkpoint` are also available as corresponding `pragma_*()` table-valued functions in `FROM` and `JOIN` queries. Schema-qualified inspection and database-scoped PRAGMA assignments work for `main`, `temp`, and attached schemas; connection-scoped PRAGMAs remain connection-scoped. `wal_checkpoint` also supports `PASSIVE`, `FULL`, `RESTART`, and `TRUNCATE` operations.

## Not supported

- Pure-Dart virtual tables are opt-in: call `registerVirtualTableModule(name, factory)` or pass `virtualTableModules` to `PureDatabase.open()`. The factory receives `create: true` for `CREATE VIRTUAL TABLE` and `false` when reconnecting a persistent schema; persistent tables must have their module registered before `open()` loads the schema. A module exposes column names and `scan()` rows with signed 64-bit rowids; INSERT/UPDATE, rowid aliases, and `RETURNING` use those rowids. Writable modules implement `replaceRows()`; its default throws a read-only-table error. The engine scans the complete module result and replaces its full row set after DML; it does not expose SQLite's query-planner/constraint-pushdown or native module ABI. `DROP TABLE` calls `destroy()` and closing/reconnecting calls `disconnect()`. Virtual tables cannot have indexes, triggers, or `ALTER TABLE` operations.
- `ATTACH DATABASE` accepts filesystem paths, `':memory:'`, empty temporary databases, and basic `file:` URIs. Shared-cache, custom VFS implementations, and custom VFS URI options are unsupported; `mode=ro` and `immutable=1` attachments reject SQL writes. ATTACH/DETACH are allowed inside transactions, but an already-read or written database cannot be detached until the transaction ends. Attached DDL, DML, maintenance, and supported PRAGMAs participate in commit, rollback, and savepoints. SQLite's atomic multi-file commit protocol is not implemented, so a crash or commit I/O failure can leave only a subset of attached files committed.
- TEMP tables, views, indexes, and triggers are connection-local and are not persisted. Triggers support `BEFORE` / `AFTER` table events and `INSTEAD OF` view events for `INSERT`, `UPDATE [OF ...]`, and `DELETE`, with `SELECT`/DML bodies and `RAISE(ABORT|FAIL|ROLLBACK, message)` / `RAISE(IGNORE)`. Direct DML against a view reports zero changed rows; trigger writes contribute to `total_changes()`.
- Column rename updates indexes, CHECKs, local and incoming foreign-key column references, local primary/unique constraints, and attached-trigger `UPDATE OF` / `OLD` / `NEW` references. Direct trigger-body `INSERT` target columns, `UPDATE` / `DELETE` target references, simple `SELECT` query blocks, and nested scalar-subquery blocks in DML expressions are also rewritten when each query block directly reads the renamed table and its references resolve unambiguously. Trigger-body `WITH`/CTE `SELECT`, `INSERT`, `UPDATE`, and `DELETE` steps are supported when their source query blocks can be rewritten independently; output aliases and explicit CTE column names are preserved. Ordinary multi-table `JOIN` query blocks are supported when the renamed-table references are qualified or otherwise unambiguous. Ordinary compound `SELECT` arms are analyzed independently, so unrelated arms remain unchanged while references in arms reading the renamed table are rewritten. Ambiguous references and compound/CTE query blocks whose source arms cannot be isolated safely remain conservatively rejected. In views, each simple query block that directly reads the renamed table is rewritten independently, including blocks inside CTEs, derived/scalar subqueries, and compound queries; qualified references and unqualified references that resolve to exactly one source are rewritten. Direct `NATURAL JOIN` and two-source `JOIN ... USING` blocks retain their join clause and follow SQLite's name-rewrite behavior; renaming a shared column can change the implicit join keys or leave a `USING` view unusable. `DROP COLUMN` rejects columns used by triggers, primary/unique/foreign-key constraints, CHECK expressions, index keys or partial-index predicates, or external foreign keys; unrelated constraints/indexes remain, but a rowid primary-key column cannot be dropped. Views are retained after dropping a referenced column: explicit references fail when queried, while wildcard projections expand against the remaining columns.
- `load_extension(X[, entry_point])` recognizes SQLite's one- and two-argument signatures but always returns `not authorized`; native shared-library loading and the SQLite native extension ABI are intentionally unsupported. Other loadable extensions beyond the bundled `base64()` / `base85()` subset are unsupported.
- PRAGMA names outside the implemented subset are ignored and return no rows; assignments to them have no effect. `PRAGMA compile_options` is implemented but returns no rows because this pure-Dart engine has no SQLite C compile-time options.

Unsupported SQL and functions raise `SqliteException`. Malformed or unsupported database-file data raises `SqliteFormatException`.

## Compatibility boundaries

### SQL and API behavior

- This is a subset engine, not a full SQLite interpreter. SQLite type affinity, coercion, and expression `NULL` behavior are not reproduced completely. `LIKE` supports `%` and `_`; matching is ASCII case-insensitive by default and can be toggled with `PRAGMA case_sensitive_like`. Do not assume SQL accepted by SQLite will work here.
- Foreign-key enforcement is off by default. `PRAGMA foreign_keys` changes are ignored inside a transaction. `PRAGMA defer_foreign_keys = ON` defers all foreign-key checks to commit (or the end of an implicit transaction) and resets after commit/rollback; `NO ACTION` can be deferred, while `RESTRICT` remains immediate.
- `PRAGMA ignore_check_constraints = ON` skips CHECK validation for subsequent writes; it does not revalidate or rewrite existing rows.
- `ALTER TABLE ... ADD COLUMN` validates a new `CHECK` against the values supplied to existing rows by the column's default (NULL passes as in SQLite). With foreign-key enforcement enabled, a new `REFERENCES` column must have a NULL default; `PRIMARY KEY` and `UNIQUE` are not allowed on added columns.
- `TEMP` tables, views, indexes, and triggers live only on their `PureDatabase` connection, even for a persistent database. Unqualified lookup prefers a same-named TEMP object, then `main`, then the oldest attached schema; dropping a TEMP object reveals the next matching object. Temporary objects disappear when the connection closes and do not change the main schema version. `PRAGMA table_list` reports their schema as `temp`, and `PRAGMA database_list` includes `temp` once its schema has been opened.
- `PRAGMA query_only = ON` blocks SQL DDL/DML and database-header/journal-mode writes on that connection; reads and connection-local settings remain available. The setting is connection-local and is not persisted.
- Trigger `RAISE(ABORT)` undoes the current statement, `RAISE(FAIL)` keeps changes already made by that statement, `RAISE(ROLLBACK)` ends the active transaction, and `RAISE(IGNORE)` skips the current row for `BEFORE` / `INSTEAD OF` triggers or the remaining statement for an `AFTER` trigger. A nested `RAISE(IGNORE)` resumes the parent trigger at its next step. These errors are surfaced as `SqliteException`.
- `AUTOINCREMENT` persists its high-water mark in `sqlite_sequence`, including across reopen; the sequence changes on inserts, not when an existing rowid is updated.
- `PRAGMA synchronous` controls explicit flushes for persistent databases: `OFF` skips commit flushes, `NORMAL` flushes rollback-journal commits and WAL checkpoints, and `FULL` flushes rollback-journal writes and WAL commits. `EXTRA` currently behaves like `FULL` because Dart's file API cannot sync the containing directory after deleting a rollback journal. Recovery writes still flush, and final durability also depends on the operating system and storage device.
- `PRAGMA cache_size` defaults to `2000` and stores the SQLite-style signed page/KiB setting per connection; it is not persisted and remains changed across transaction rollback. This engine has no separately tunable page cache, so the setting does not change its memory use or I/O strategy.
- `PRAGMA threads` is connection-local, defaults to `0`, ignores negative assignments, and clamps positive values to `8`; it records SQLite's worker-thread limit but does not parallelize this engine's query execution. `PRAGMA mmap_size` accepts assignments but remains `0` for persistent files and returns no rows for in-memory/TEMP databases because this engine does not memory-map database files. `PRAGMA shrink_memory` is accepted as a no-op because there is no separately managed page cache to release.
- `PRAGMA secure_delete` accepts `OFF` (0), `ON` (1), and `FAST` (2). `ON` zeros pages returned to the freelist and rewritten B-tree records, including overflow pages; `FAST` clears rewritten B-tree records but can leave old bytes in freelist pages. Unqualified assignments also update TEMP and attached schemas, and newly attached schemas inherit the main setting. This is not a secure-erase guarantee for old WAL/journal frames, backups, virtual-table-owned data, or storage-media remanence.
- `PRAGMA default_cache_size` stores a positive page count in the database header and persists it across reopen; negative assignments are stored as their absolute value, while zero clears the header field and reads back as `-2000` (SQLite's default). It also updates the connection's `cache_size` value, but neither setting alters this engine's actual memory use. In-memory databases keep the setting on that connection only.
- `PRAGMA analysis_limit` is connection-local and defaults to `0`; negative assignments are ignored. `ANALYZE` always records the exact indexed-row count. A positive limit estimates per-prefix averages from at most that many leading index entries, plus a second sample of that size when the first sample contains only one leading-key value. The sample is deterministic and may differ from SQLite's sampling estimates; entry materialization still visits the full index, and statistics do not affect this engine's query planning.
- `PRAGMA max_page_count` is connection-local for persistent databases, defaults to the upstream `4294967294` (SQLite builds may lower it with `SQLITE_MAX_PAGE_COUNT`), and cannot be set below the current page count. A write that needs additional pages at the limit fails with `SqliteException: database or disk is full`; in-memory databases do not have page-backed storage, so setting this PRAGMA there is rejected.
- TEMP PRAGMAs have connection-local state. TEMP starts with `schema_version = 0`, which changes when TEMP schema objects change; its `application_id` and `user_version` do not affect `main`. `application_id`, `schema_version`, `user_version`, and `default_cache_size` roll back with SQL transactions/savepoints; `page_size` changes survive rollback. `cache_size`, `max_page_count`, `journal_size_limit`, and `journal_mode` also remain changed after rollback; `busy_timeout` and `wal_autocheckpoint` remain connection-wide. TEMP always reports `synchronous = OFF`; assignments are ignored, and attempts inside a transaction are rejected. TEMP has no page-backed pager in this engine: page counts remain zero, and its reported page-size, max-page-count, synchronous, journal-mode, and journal-limit settings do not configure physical I/O or durability. `journal_size_limit` is scoped to one database (`main`, `temp`, or an attached schema), not shared across attached schemas.
- `PRAGMA page_size` accepts valid SQLite page sizes before the main database has schema objects. For persistent databases, it applies only to a database created by the current connection before any other file write; setting it on a reopened file, after a write, or in WAL mode is ignored. In-memory databases retain the selected setting before schema creation, and transaction rollback restores it.
- `PRAGMA legacy_alter_table` is connection-local, defaults to `OFF`, and is not rolled back with a SQL transaction. When enabled, `ALTER TABLE ... RENAME TO` updates the table definition and associated index/trigger targets but leaves view SQL, trigger bodies, CHECK expressions, and partial-index predicates unchanged. Foreign-key parent references are updated only when `PRAGMA foreign_keys` is enabled, matching current SQLite behavior.
- `VACUUM` rebuilds and compacts a persistent `main` or attached database in rollback-journal or WAL mode, preserves schema and header settings, and clears freelist pages; `VACUUM temp` and in-memory `VACUUM` are no-ops because those databases have no persistent pages. `VACUUM schema INTO filename` writes a compact, independent rollback-journal database from the selected `main` or attached schema—including an in-memory source—without changing the source; the destination may be new or empty. `VACUUM INTO` is rejected inside a transaction and is not supported for `temp`.
- `REINDEX` rebuilds all indexes, or indexes selected by table, index, or built-in `BINARY` / `NOCASE` collation name; schema qualification works for `main`, `temp`, and attached databases.
- `ANALYZE` maintains `sqlite_stat1` rows with exact counts when `analysis_limit` is zero and sampled prefix averages when it is positive. Statistics are persisted and readable but do not affect query planning in this engine. `main`, `temp`, and attached schemas are supported; analyzing a TEMP target stores stats in the connection-local TEMP schema.
- `PRAGMA reverse_unordered_selects = ON` reverses rows for simple table queries without `ORDER BY` as a diagnostic (before `LIMIT` / `OFFSET`); explicit `ORDER BY` retains its requested order.
- `PRAGMA read_uncommitted` is connection-local. It records and returns the requested setting, but has no isolation effect because shared-cache connections are unsupported; reads remain serializable, as in SQLite without shared cache ([SQLite isolation rules](https://www.sqlite.org/pragma.html#pragma_read_uncommitted)).
- `PRAGMA automatic_index` is connection-local and stores/reports the ON/OFF setting; it has no query-plan effect because this engine has no automatic-index planner.
- `PRAGMA count_changes` is connection-local and defaults to `OFF`. When enabled, `PureDatabase.select()` on an INSERT/UPDATE/DELETE without `RETURNING` returns one row named `rows inserted`, `rows updated`, or `rows deleted`; the count covers direct statement rows, not trigger or foreign-key side effects. `execute()` continues to return its normal changed-row count.
- `PRAGMA full_column_names` defaults to `OFF`; `short_column_names` defaults to `ON`. They affect labels for unaliased projected column references: full names or disabling short names retains the table qualifier, while the default strips it. Explicit `AS` aliases and `*` projections are unchanged.
- `PRAGMA journal_mode` is connection-local except for persistent `WAL`, which is recorded in the database header. Rollback-journal `DELETE`, `TRUNCATE`, and `PERSIST` use the same recovery journal with their corresponding commit cleanup; `MEMORY` and `OFF` retain a whole-database rollback snapshot in memory and do not create a disk journal. Both modes permit in-process rollback but cannot recover a write interrupted by a process crash. In-memory databases report `MEMORY` by default. Changing persistent journal mode inside a transaction is rejected.
- `PRAGMA temp_store` accepts `DEFAULT` (0), `FILE` (1), and `MEMORY` (2), connection-wide. Changing its value outside a transaction clears all TEMP objects and resets TEMP header settings; changing it inside a transaction is rejected. `FILE` reports the requested setting only: TEMP storage remains in memory because this engine has no disk-backed TEMP pager.
- `ORDER BY` supports explicit `NULLS FIRST` / `NULLS LAST`; without a modifier, NULL sorts first in ascending order and last in descending order.
- `PRAGMA pragma_list` reports only implemented PRAGMAs. Other pragma names and their assignments are ignored, matching SQLite's unknown-pragma behavior but not implementing the setting; `PRAGMA function_list` returns `name`, `builtin`, `type`, `enc`, `narg`, and `flags` for built-in and registered scalar, aggregate, and window functions. `PRAGMA compile_options` returns an empty list, `sqlite_compileoption_get()` returns `NULL`, and `sqlite_compileoption_used()` returns `0` because SQLite C compile-time options do not apply to this engine.
- `PRAGMA wal_checkpoint(NOOP)` reports `busy`, committed WAL frame count (`log`), and `checkpointed`; outside WAL mode the last two values are `-1`. `PASSIVE`, `FULL`, and `RESTART` copy committed frames to the database and reset the WAL when the operation completes; `TRUNCATE` also empties the WAL file. `PASSIVE` does not wait and reports no checkpoint progress if the engine cannot acquire its locks; the other modes report `busy = 1` when they cannot proceed within `busy_timeout`. `PRAGMA wal_autocheckpoint` is connection-local, defaults to `1000`, and runs a non-waiting checkpoint after a commit once that many WAL frames have accumulated; non-positive values disable it. This engine does not use SQLite's shared-memory WAL index, so it cannot coordinate checkpointing with concurrent native SQLite readers or writers; do not checkpoint while another native SQLite connection is using the same file. `NOOP` reports `checkpointed = 0`, which can differ from native SQLite's checkpoint progress.
- `PRAGMA journal_size_limit` is database-scoped and defaults to `-1` (no limit). A nonnegative value caps the retained WAL file after a successful checkpoint and the retained rollback journal after a `PERSIST` transaction; `0` leaves either file empty. It takes effect at commit/checkpoint, not when assigned. `DELETE` journals are removed and `TRUNCATE` journals are emptied at commit regardless of the limit.
- `sqlite_log(code, message)` returns `NULL` and calls the optional `onLog` callback supplied to `PureDatabase.memory()` or `PureDatabase.open()`. Without a callback it is silent; callback exceptions are ignored so they cannot fail the SQL statement.
- `OR FAIL` preserves earlier rows changed by the statement; `OR ROLLBACK` rolls back an active SQL transaction on UNIQUE, NOT NULL, or CHECK conflicts. Foreign-key failures retain ABORT behavior.
- UPSERT conflict targets may name columns or structurally matching deterministic index expressions, with optional `COLLATE` and sort direction. The explicit collation and partial-index predicate must match the unique key; expressions using nondeterministic or user-defined functions are rejected in indexes.
- `changes()`, `total_changes()`, and `last_insert_rowid()` are connection-scoped. `changes()` reports only the outer DML row count, `total_changes()` includes trigger DML, and `last_insert_rowid()` is restored after a trigger finishes. Trigger bodies run in the outer statement transaction; recursive re-entry of an active trigger is suppressed by default and enabled by `PRAGMA recursive_triggers = ON`, with a 1,000-level depth limit. Foreign-key cascades run child-table DELETE triggers; `OR REPLACE` runs DELETE triggers for replaced rows only when recursive triggers are enabled. Dropping a table does not run that table's own DELETE triggers.
- User-defined aggregate callbacks receive materialized per-group or per-window-frame argument rows; `DISTINCT` is supported for a single aggregate argument. Window-only callbacks receive the ordered partition arguments, zero-based current-row index, and frame arguments after `EXCLUDE`; the incremental inverse/value state API is not exposed.
- Aggregate `FILTER (WHERE ...)` keeps only rows whose filter expression is true; false and NULL rows are excluded. It applies to built-in and registered aggregates, including aggregate window functions, but not scalar or window-only functions.
- `unhex()` returns `NULL` for invalid or unpaired hex digits. Its optional ignore-set skips non-hex separators only between complete byte pairs; a separator cannot split the two digits of a byte, and hex digits listed in the ignore-set remain data.
- JSON functions accept strict JSON and JSON5 text and SQLite JSONB blobs through the listed `json*` / `jsonb*` functions. JSONB uses SQLite's binary format and is exposed to Dart as `List<int>`; JSONB functions return blobs, including `jsonb_each` / `jsonb_tree` container values. `json_valid(X[, flags])` supports strict/JSON5 text flags `0x01` / `0x02` and superficial/deep JSONB flags `0x04` / `0x08`. Text-producing functions return canonical strict JSON. `json_array_insert` paths must end in an array index. `json_each` and `json_tree` expose `key`, `value`, `type`, `atom`, `id`, `parent`, `fullkey`, and `path`; each walks immediate children (or the primitive root), while tree includes the selected node and descendants. They accept a JSON argument and optional path, including correlated joins with `INNER`, `LEFT`, `RIGHT`, `FULL`, and `CROSS` join forms. `->` returns JSON text and `->>` returns an SQL scalar (or JSON text for arrays/objects); their right operand may be a path, object label, or array index. `json_error_position` reports zero for valid strict JSON, JSON5, or JSONB and otherwise uses the Dart parser's error offset, so its position is not guaranteed to match SQLite for every malformed input. `json_pretty` accepts an optional text indentation string, defaulting to four spaces. Paths support `$`, dot members (including quoted member names), array indexes, `[#-N]` from-end indexes, and `[#]` append for modification. JSON arrays/objects are plain SQL text and do not retain SQLite's JSON subtype for nested-function semantics.
- `subtype()` reports `74` for direct JSON text results, JSON object/array extraction, `->`, and JSON text aggregates. It propagates through `COALESCE` / `IFNULL` / `IF` / `IIF`, `CASE`, `CAST`, `NULLIF`, and likelihood wrappers; it does not retain subtype metadata through stored columns, subqueries, arbitrary functions, or nested JSON value construction.
- `unistr()` decodes PostgreSQL-style fixed-width Unicode escapes and escaped backslashes; malformed escapes remain literal. `unistr_quote()` escapes C0 control characters for SQL display.
- `LOWER()` / `UPPER()` only fold ASCII letters; `QUOTE()` truncates text at the first embedded NUL, matching SQLite's text-literal representation.
- `SOUNDEX(X)` uses SQLite's ASCII letter/code mapping and returns `?000` for NULL or text without ASCII letters. SQLite exposes this function only when built with `SQLITE_SOUNDEX`; this engine always includes it.
- `sqlite_offset(X)` returns the byte offset of the table record for a direct column from a persistent ordinary `main` table. Computed expressions, derived/TEMP rows, and in-memory rows return `NULL`. This engine reads table records even when an index filters rows, so it does not report index-record offsets. SQLite itself exposes this function only when built with `SQLITE_ENABLE_OFFSET_SQL_FUNC`; this engine always includes it ([SQLite documentation](https://www.sqlite.org/lang_corefunc.html)).
- `median()`, `percentile()`, `percentile_cont()`, and `percentile_disc()` ignore NULL samples, require finite numeric samples and parameters, and use SQLite's continuous interpolation or lower-discrete rank rules. `percentile()` uses 0–100; the other percentile forms use 0–1. Per-row percentile parameters may differ by less than 0.001.
- `format()` / `printf()` cover SQLite's documented conversions and flags, including SQL quoting, width, precision, grouping, null handling, and alternate-form floating output. Width/precision are capped at 1,000,000; floating conversions round binary64 values to at most 16 significant digits, or 26 with `!`. Last-digit text can differ from a particular SQLite build's formatter.
- Recursive CTE evaluation processes one queued row at a time. `ORDER BY` controls queue priority, `LIMIT` caps rows added to the result, and `OFFSET` skips output rows while still recursing from them. Anchors may use compound operators; recursive arms must share their boundary's `UNION` or `UNION ALL` mode.
- CTE materialization hints are accepted but do not change the execution strategy; CTEs are materialized.
- `CREATE TABLE ... AS SELECT` materializes the query, infers declared column types from SQLite expression affinity, and uniquifies duplicate result names; it creates no constraints.
- Window functions run over the rows remaining after `GROUP BY` and `HAVING`; grouped aggregate expressions in window arguments, partitioning, and ordering are evaluated per group before the window frame.
- Window aggregates use the default frame (`RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`) when no frame is specified. Explicit `ROWS` / `GROUPS` / `RANGE` frames support `EXCLUDE NO OTHERS`, `CURRENT ROW`, `GROUP`, and `TIES`; `RANGE` offsets are constant non-negative numeric expressions and require exactly one effective `ORDER BY` term. Inline and named windows can chain from a previously defined base window; as in SQLite, a derived window cannot add `PARTITION BY`, override an inherited `ORDER BY`, or inherit a base window that has a frame. Chaining resolves only earlier definitions; a forward or unknown base inside a window definition contributes no inherited clauses, while direct `OVER missing` references fail.
- Transaction mode keywords are accepted, but do not provide SQLite's full distinction between deferred, immediate, and exclusive transaction semantics.
- SQL savepoints are case-insensitive, nest in stack order, and can roll back DML and schema changes; `ROLLBACK TO` keeps its target savepoint active, while releasing the outermost savepoint commits its transaction. Nested calls to the Dart `transaction()` callback remain unsupported for persistent databases.

### SQLite files and runtime

- Persistent storage uses `dart:io` and works on Dart VM, not Dart Web. `sqlite3.open(':memory:')` is not supported; use `PureDatabase.memory()`.
- The engine reads and writes SQLite 3 database files only when their schema and operations fit the supported subset. File-format compatibility does not imply SQL or feature compatibility for arbitrary SQLite databases.
- Rollback-journal files and WAL files are supported. WAL is scanned directly rather than through SQLite's shared-memory wal-index. Readers can see the last committed snapshot while a WAL writer is active; switching to `DELETE` checkpoints committed WAL pages. Automatic WAL checkpointing uses the connection's `wal_autocheckpoint` threshold.
- File locks and `busy_timeout` are implemented, with tests for interaction with native SQLite processes. Do not run simultaneous native SQLite writers against a database while this engine is open, especially in WAL mode.
- The package tests check representative SQLite CLI interoperability, journal recovery, locks, and WAL behavior. Passing them does not establish full SQLite compatibility or validate every application migration/query.

### `sqlite3` facade

For existing code that uses only the small facade, the import and call pattern can be switched:

```dart
import 'package:dart_sqlite/dart_sqlite.dart';

void main() {
  final db = sqlite3.open('data/app.sqlite');
  try {
    db.execute('INSERT INTO users (name) VALUES (?)', ['Ada']);
    print(db.updatedRows);
    print(db.select('SELECT id, name FROM users ORDER BY id').first['name']);
  } on SqliteException catch (error) {
    print(error);
  } finally {
    db.dispose();
  }
}
```

The facade provides `sqlite3.open(path)`, `Database.execute`, `Database.select`, `Database.updatedRows`, `Database.dispose`, `Row`, `ResultSet`, and `SqliteException`. It does not provide the complete `package:sqlite3` API (for example, prepared-statement objects or `sqlite3.open(':memory:')`). Use `PureDatabase` when the in-memory API or transaction callback is needed.
